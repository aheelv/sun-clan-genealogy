# 孙氏族谱 · 中秋主题静态族谱站点

以**中秋**为主题的静态族谱站点。将《孙氏族谱》的世系图表（xlsx）与文献部分（doc）转录、建模为通用族谱数据，提供**图形化谱系呈现**、完整增删改查、三层校验机制与角色权限治理。

> **零构建**：原生 ES Modules，无打包器、无 CDN 依赖。双击 `index.html` 即可使用。

---

## 快速开始

```bash
# 方式一：直接打开（file:// 亦可，种子数据已内联）
双击 index.html

# 方式二：本地服务器（推荐，便于开发调试）
npm run serve      # → http://127.0.0.1:5173/

# 运行全部自检（独立交叉校验 + 模块图 + 逻辑层 + 渲染层）
npm test
```

## 谱系图形（主视图）

图形是本项目的呈现主体，因此它的视觉语言被设计成**可直接读出语义**：

| 视觉 | 含义 |
| --- | --- |
| 实线 · 青玉 | 文献明载的父子关系 |
| 实线 · 月华金 | 主干行明载的父子关系 |
| 虚线 · 陶土 | 规则推导、待人工复核 |
| 短虚线 · 朱砂 | 婚姻关系 |
| **弧线** · 朱砂 | **过继关系**（与父系正交折线刻意区分，使生父与养父可同时读出） |
| 虚框 · 淡底 | 配偶 |
| 节点角标「出继」/「入继N」 | 过继身份 |
| 浅色横带 ·「N世」 | 世代背景带 |

**绘制单元是「主干人物 + 配偶」而非单人**：配偶横向并列于主干右侧，子女挂在**主干**之下，故世代线始终沿主干延续。

**谱系图默认参数 = 纵向铺展 · 始祖以下 2 代（23 人）· 含配偶**（站点默认落点为「概览」，见上）

世代自上而下堆叠（一世 → 二世 → 三世），符合谱牒「上为尊」的阅读习惯。默认只展开始祖以下 2 代，是因为**谱系图一旦缩到极小就失去意义**：全谱 157 人时整树宽 8,846 px，纯按宽度适应会得到 `scale≈0.109`、字号 **1.4 px**，整张图退化成一条横向细线。默认取 23 人后适应比例为 `0.6`（字号约 7.8 px），开箱即是一棵看得清的树。

**可读字号下限（minScale = 0.5）**：适应变换不再无底线缩小。一旦用户展开到更宽的范围（如 4 代），图形宁可**溢出画布**、由用户拖拽平移查看，也不缩到读不出字；溢出时状态栏会明确提示。放得下则自动居中，放不下则以**根人物**为锚居中，保证「从始祖看起」。

**纵向舒展层距**：世代数少时纵向会留下大片空白。由于纵向布局的**宽度与层距无关**，可在不改变横向适应比例（也就不会让节点变小）的前提下把世代间距拉开（上限 2.2 × 基准层距），让纵向空间被真正利用。

**加载即适应，尺寸变化自动重算**：首屏在容器尚未完成布局时会先按兜底尺寸绘制一版，下一帧按真实尺寸重算；此后由 `ResizeObserver` 监听画布，窗口缩放、侧栏展开都会自动重新适应，直到用户手动平移或缩放为止。

**布局算法为轮廓法（Reingold–Tilford 思路）**：先后序摆好子代，再用左右轮廓求兄弟间最小不重叠位移，最后把父节点锚定于首末子节点中心的中点——于是「父节点恰好居中于其子节点之上」成为**恒等式而非近似**（实测 433/433 = 100%），且同层永不重叠。全谱 1,546 节点布局约 3–11 ms。

**交互**：点击节点看档案 · 点击 `+`/`−` 折叠展开（显示隐藏后代数）· 滚轮缩放 · 拖拽平移 · 双击改根 · 触屏单指横移 / 双指捏合 · `/` 聚焦检索 · `g` 回图谱。

## 校验体系（三层）

| 引擎 | 位置 | 回答的问题 |
| --- | --- | --- |
| **独立交叉校验** `C01`–`C12` | `tools/verify_data.py` | **原始文件的内容抓取准不准**。校验器与建模器不共享一行代码，只读原谱逐格转录独立重算分页、列→世代映射、主干链、候选父，再与建模产出逐项比对 |
| **构建期校验** `V001`–`V015` | `tools/build_data.py` | 转录与建模质量如何（发现问题即回头改脚本） |
| **运行时校验** `F-`×4 + `R-`×10 + `G-`×11 = **25 条** | `assets/js/core/validate.js` | 使用者编辑后的数据还对不对（持续守护） |
| **误合并排查**（独立） | `tools/diagnose_merge.py` | **同名异人有没有被错并成一条**。只读原谱转录与产出，按版式几何独立重算每个出现格的「邻接父」，若同一记录的多格给出**不同**的邻接父，即判为疑似误合并 |

**独立交叉校验 12/12 通过，已知留白 4 处**（原谱第 6 页 E326–H326 四格「万氏／宋氏／宫氏／崔氏」未记明夫主）。它把「转录本身是否忠实」与「原谱本身是否有缺口」分成两类证据——前者必须全绿，后者逐条列明理由。

**这套机制实际抓出了 8 个真实缺陷**（全部已修）：配偶字段双向重复（766 例）、过继语义误判、过继关系重复计数（15→12）、**同名异人误合并（128 组）**、**旁注按行距挂接而忽略列位（误改 2 人的生父）**、**过继目标在同名养父间歧义**，以及校验器自身的三处误报。

其中后三类由一次「同名异人」排查连带发现——见 [根因与修复](#根因同名异人误合并)。

## 数据模型要点

- **单一事实来源**：`persons` 是唯一事实来源；父子由 `fatherId` 派生，婚姻由 `spouseOfId` ↔ `spouseIds` **互斥双向**表达（配偶自身的配偶列表恒为空）。
- **溯源优先**：每条记录保留原谱出处 `[页, 行, 列, 原文]`，可回溯到 xlsx 的具体单元格。2,154 条出处全部可回溯。
- **置信度显式化**：`doc`（文献明载 8）/ `spine`（主干行 49）/ `note`（旁注明载 3）与 `heuristic`（规则推导）严格区分。当前 **884 / 944 条父子关系为推导所得（93.6%）**，全部标注并在校验中心集中列出待人工复核。
- **人物身份键（`pkey`）**：同世代同名**不等于**同一人。判定的唯一依据是**递归身份键** `pkey(人) = (世代, 姓名, pkey(父))`——父的身份不同，则同名的两人是两个人。父子世代差恒为 1（`V002 = 0`），故递归必然终止。**绝不用「姓名 + 世代」作合并键**，那正是误合并的根源。
- **过继语义**：旁注「过继给X为子」写在**生父所在行**，故 `fatherId` 恒为生父；养父另立 `adoption` 关系并按 `(出继子, 养父)` 去重。13 条过继关系**没有一条**的 `fatherId` 等于养父。反向旁注「为X之N子过继」则**指名生父**（`parentEvidence: note`），两者方向相反，须分别归类。
- **不猜原则**：无法判定处一律留白并标记待考，不臆造结论。族谱是不可再生的史料，宁可留下待考标记，也不制造看似完整实则错误的谱系。

## 根因：同名异人误合并

### 症状

原谱中存在两个「智广」，同属十三世、分居两支。旧版把它们**并成一条记录**，于是两人的配偶与子女被堆到同一条上，谱系读起来「一个人横跨两支」——这正是族谱最不能容忍的错误。

### 根因

族谱用**凡字**命名：同辈男丁共用一字（十三世皆含「广」）。因此 **「同名 + 同世代」在原谱中大量存在，绝不等于同一人**。旧版建模把「姓名 + 世代」当作归并键，凡同世同名一律合并，于是：

1. 两个智广被并成一条；
2. 配偶取并集、子女取并集，两支的血缘被搅在一起；
3. 更隐蔽的是——**判定「是否同一人」与判定「父系是否有分歧」用了两套口径**：前者比姓名，后者比**单元格引用**。同一个人在原谱中常有多格出处，于是「同一个父亲、不同的格子」被误读成「父亲有分歧」，把大量本无争议的人推进了「拆分」分支。

### 修复

| # | 改动 | 说明 |
| --- | --- | --- |
| 1 | **统一身份函数** `pkey`（R10） | 归并与分歧检测**共用**同一个递归身份键 `pkey(人) = (世代, 姓名, pkey(父))`。父的身份不同 → 同名的两人是两人；父相同 → 无论出现在多少格，都是同一人。父子世代差恒为 1，递归必然终止；`parent_of` 变更时同步失效记忆化缓存 |
| 2 | **旁注列位感知**（R3） | 原谱旁注写在**被注人自己的列**或**其次代列（列号 +1）**，行号相同或相邻。旧实现按「行距优先」取最近者，导致 `D1710「为纾之四子过继」` 被挂到同行的 `I1710`（跨 5 列、毫不相干）。改为 `(是否同列/次代列, 行距, 列距)` 分层排序 |
| 3 | **生父旁注规则** `birth_father`（R9b） | 「为X之N子过继」「（X之N子过继）」**指名生父**，与「过继给Y为子」（指名养父）方向相反。新规则置于通用「过继」规则**之前**匹配，并把生父写入 `fatherId`（`parentEvidence: note`） |
| 4 | **过继目标消歧** | 「过继给X为子」的 X 若是重名者，须取**与出继人同一主干行**的那一位，而非另一位同名者 |
| 5 | **V014 收敛** | 分歧已被旁注（生父/过继）解释的组，不再计入「无法解释的父系冲突」 |
| 6 | **独立排查工具** `diagnose_merge.py` | 与建模器不共享一行代码，按版式几何独立重算每格的「邻接父」，交叉验证无残留误合并 |

### 结果

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| 同名异人拆分组数（`V005` / `V016`） | 0（全被误并）／ 182（虚高） | **128 / 128**（两口径一致） |
| 无法解释的父系冲突（`V014`） | 误报 | **0** |
| 误合并疑似记录（独立排查） | 95 条 | **0 条**（206 条多出处记录全检） |
| 人物记录数 | 1,550 | **1,752** |
| 过继关系 | 12 | **13** |
| 独立交叉校验 | 11 / 12 | **12 / 12** |

两个智广修复后：`P0905`（仁支，父 世伦，配 徐莉）与 `P0919`（礼支，父 世峰，配 杨永梅，子 大睿）——**父系、支系、配偶、子女各自独立**。

## 权限设计

四级角色 × 13 项权限，矩阵在 `core/auth.js` 中集中定义，界面与文档均从它渲染。

| 角色 | 能力 |
| --- | --- |
| **访客** | 只读浏览、查阅校验报告 |
| **编修** | 新增 / 修改人物与关系、导出数据（不可删除、不可改世代与支系） |
| **族老** | 编修 + 删除 + 导入 + 查阅审计日志 |
| **管理员** | 全部权限，含数据重置与角色管理 |

**角色切换口令闸门**：以「访客」浏览免口令；切换到其他任何角色都需输入口令（常量定义在
`core/auth.js` 的 `ACCESS_PASSWORD`）。通过后本会话（标签页）内有效，非访客之间互切不再重复索要；
切回「访客」即重新上锁，刷新页面需重新输入。本地持久化的角色**不作为授权依据**——
否则只要本地存过一次 `admin`，刷新即可绕过口令。

> ⚠️ **安全边界**：本站为静态站点，数据存于浏览器 localStorage。角色机制用于**协作约束与操作留痕**，不具备密码学安全性。角色切换口令同样只是**前端软门槛**——口令常量随代码下发，查看源代码即可读到，控制台执行 `auth.setRole('admin')` 亦可绕过。它只防误操作与好奇浏览，**不能替代访问控制**。若需真实鉴权，应将同一份权限矩阵迁移到服务端 API 层复用。

## 技术选型说明

| 选择 | 理由 |
| --- | --- |
| **零构建** | 站点逻辑无编译需求。十年后仍能直接打开，无需复活已过期的工具链 |
| **种子内联** | `fetch` 在 `file://` 下被同源策略拦截。内联后双击即可用，便于长期保存与传承 |
| **关系派生而非冗余** | 只存 `fatherId`/`spouseOfId`，关系在读取时派生，杜绝"关系表与人物表打架" |
| **布局引擎独立成层** | `domain/layout.js` 纯函数、零 DOM，可在 Node 中直接断言「同层不重叠、父节点居中、布局确定」等不变量——图形正确性不依赖目视检查 |
| **轮廓法而非矩形打包** | 绘制单元「主干 + 右侧配偶」左右不对称，矩形打包会让父节点偏位；轮廓法使居中成为恒等式 |
| **默认纵向 + 有限视野** | 谱牒习惯「上为尊」，且全谱 157 人宽 8,846 px，横向适应后字号仅 1.4 px。默认纵向 + 2 代，把「看得清」放在「看得到」之前 |
| **缩放下限而非无条件适应** | 无底线的「适应窗口」会把谱系图压成一条细线。设 0.5 下限，溢出交给用户平移——可读性优先于完整性 |
| **手写 Store** | 1,752 人的数据量与交互复杂度不需要状态库；手写 300 行的可读性优于引入依赖 |
| **规则注册表校验** | 规则为纯数据 + 纯函数，新增规则不改引擎；同一套规则供表单实时校验与全谱校验复用 |
| **校验器与建模器解耦** | 同一份代码无法发现自己"理解错了原谱"。独立重算是唯一能证伪建模假设的办法 |
| **MS-DOC 直接解析** | 环境无 Office，且转换工具会丢失域与表格边界信息。按规范解析保真度最高 |
