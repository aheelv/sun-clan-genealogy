## 2. 转录方法

### 2.1 xlsx 转录 — `tools/extract_xlsx.py`

**策略**：**逐格无损转录，不做任何解释**。

对 `Sheet1` 的每一个非空单元格，输出：

```json
{ "row": 1, "col": 1, "ref": "A1", "value": "                       孙氏世系图表                              第01页" }
```

同时记录 `mergedRanges`（64 处）、`maxRow`、`maxCol`、`cellCount`。

**为什么先无损转录再解释？** 把「读取」与「理解」彻底分离：

- 转录层只保证**一个字都不丢、一个格子都不错位**；
- 解释层（`build_data.py`）可以反复迭代推导规则，而无需重新读取源文件；
- 转录结果可被独立工具交叉验证。

**交叉验证**：转录结果与独立读取（经由 `tencent-docs-sheetagent` 子代理）逐格比对，**2,779 个单元格与 64 处合并区间完全一致**。

### 2.2 doc 转录 — `tools/extract_doc.py`

**挑战**：Word 97-2003 是**二进制复合文档格式**（OLE2/CFB），不能当作纯文本读取，且环境中未安装 Word / WPS / LibreOffice。

**解法**：按 **MS-DOC 规范**直接解析，仅依赖 `olefile` 一个库。

解析链路：

```
.doc 文件（OLE2 复合文档）
   │
   ├─▶ 打开 WordDocument 流，读 FIB（File Information Block）
   │      · 偏移 0x0A 读 flags，位 9 判定 fWhichTblStm
   │      · 据此选择 0Table 或 1Table 流
   │
   ├─▶ 从表流读 Clx（分片表索引）
   │      · 定位 PlcPcd（分片描述符数组）
   │
   ├─▶ 逐分片解析 Pcd（Piece Descriptor）
   │      · fc：文件字符位置
   │      · 位 30（fCompressed）：0 = UTF-16LE，1 = ANSI(cp936)
   │
   └─▶ 按分片编码还原正文，拼接为完整文本
          · compressed 分片：单字节解码，先试 cp936，失败回落 cp1252，
            fc 需右移 1 位（原值以「半字节」为单位存储）
          · 非压缩分片：UTF-16LE 解码
          · 解码失败一律 errors="replace" 兜底，绝不因单字节异常中断整篇提取
```

**特殊控制字符处理**

| 字符 | 含义 | 替换为 |
| --- | --- | --- |
| `\x01` | 内嵌图片 | 【图】 |
| `\x07` | 单元格／行结束 | `␞`（保留表格结构信息） |
| `\x08` | 图形 | `␈` |
| `\x0b` | 手动换行 | `\n` |
| `\x0c` | 分页 | `\f` |
| `\x09` | 制表符 | `\t` |
| `\x13`/`\x14`/`\x15` | 域标记 | 移除 |
| `\x1e` | 不换行连字符 | `‐` |
| `\xa0` | 不换行空格 | 空格 |

保留 `\x07`（单元格结束）是刻意的：目录页的表格结构正是靠它还原的（见 `intro.json` 的 `TOC.raw`），替换为 `␞` 既保留了结构信息，又不破坏纯文本可读性。

**为何不直接把 `.doc` 转成 `.docx` 再读？** 转换工具（LibreOffice 等）会重排文本、丢失域与表格边界信息，且引入外部重依赖。按规范直接解析虽然代码量更大（`extract_doc.py` 共 141 行），但**保真度最高、依赖最少、可长期复现**。

### 2.3 建模 — `tools/build_data.py`

把空间布局还原为谱系语义，规则 R1–R10 详见 `docs/03-数据模型与校验规范.md`。

关键步骤：

1. **分页与世代映射**：以标题行切分 31 页，从表头行建立「列 → 世代」映射；
2. **单元格分类**：人名 / 配偶（`X氏`）/ 旁注 / 未具名占位；
3. **主干行识别**：横向连续填写者构成显式世系链（32 条）；
4. **配偶归属**：夫妻相并 + 凡字判性（R2a）；
5. **父子推导**：主干行（`spine`）→ 文献（`doc`）→ 启发式最近行（`heuristic`）；
6. **实体归并**：键 `(gen, name, fatherName)`，同名异人（R8）除外；
7. **过继处理**：旁注「过继给X为子」记在生父行 → `fatherId` 为生父，养父另立 `adoption` 关系并按 `(出继子, 养父)` 去重；
8. **支系传播**：三世祖头名 + 父系继承（R7）；
9. **校验**：执行 V001–V019，输出报告。

### 2.4 独立交叉校验 — `tools/verify_data.py`

**这是本项目对「原始文件的内容抓取需反复校验以保证准确性」的核心机制。**

校验器与建模器**不共享一行代码**，只读两个文件：`data/source/chart-raw.json`（原谱逐格转录，事实基线）与 `data/genealogy.json`（建模产出，受检对象）。分页、列→世代映射、主干链、最近行候选父等推导全部独立重算一遍，再与建模产出逐项比对。

```bash
python tools/verify_data.py            # 输出报告并打印摘要
python tools/verify_data.py --strict   # 任一 FAIL 时以非零码退出（已接入 npm test）
```

结果写入 `data/verification-report.json`（C01–C12，12 项全部通过，已知留白 4 处），并随 `emit_seed.py` 入站展示。

**为什么必须独立重算，而不能只靠构建期校验？** 构建期校验与被检对象出自同一份代码，只能发现「规则内部不自洽」，无法发现「规则本身理解错了原谱」。独立重算引入了第二套实现——两边一致才说明管线无实现缺陷。事实上这套机制抓出了 **6 个真实缺陷**（配偶字段双向重复、过继语义误判、过继关系重复计数、C05/C07/C11 的校验器自身误报），详见设计文档 §5.1。

### 2.5 打包 — `tools/emit_seed.py`

将 `data/*.json` 打包为 `assets/js/data/seed.js`：

```js
export const SEED = { meta, intro, persons, adoptions, buildReport, verification, ... };
```

**为什么要内联而不是 fetch？** `fetch('./data/x.json')` 在 `file://` 协议下会被浏览器同源策略拦截。内联后，**双击 `index.html` 即可使用**，无需任何服务器——对族谱这类需要长期保存、可能传给后人的资料，这一点非常重要。

## 3. 可复现性

### 3.1 完整重跑

```bash
# 1) 转录原始资料（读取 D:\book\cert pic\ 下的两个文件）
python tools/extract_xlsx.py
python tools/extract_doc.py

# 2) 建模（含构建期校验 V001–V019）
python tools/build_data.py

# 3) 独立交叉校验（与建模脚本不共享代码；--strict 有 FAIL 即非零退出）
python tools/verify_data.py --strict

# 4) 打包为浏览器可加载的种子
python tools/emit_seed.py

# 或一步到位
npm run extract && npm run build:data && npm run verify

# 全部自检（独立校验 + 模块图 + 逻辑层 + 渲染层）
npm test
```

### 3.3 确定性

管线是**纯函数式**的：相同输入必然产生相同输出（除 `generatedAt` 时间戳外）。因此 `data/*.json` 的 SHA-256 可作为**建模结果的校验基线**——若规则被修改，指纹变化能立即反映出来。

## 4. 数据质量声明

### 4.1 可信度分层

| 类别 | 数量 | 占比 | 可信度 |
| --- | :-: | :-: | --- |
| **文献明载**（`doc`） | 8 | 0.8% | 高。《前言》正文所述，可逐字核对 |

| **旁注明载**（`note`） | 3 | 0.3% | 高。「为 X 之 N 子过继」等旁注直接指名生父 |
| **规则推导**（`heuristic`） | 884 | 93.6% | **中，须人工复核** |
| 父子关系合计 | 944 | 100% | |

### 4.2 必须告知使用者的三点

1. **93.6% 的父子关系是推导所得**，依据是「相邻世代列中行距最近的男性」这一版式假设。该假设在原谱排版规整时成立，但排版异常处可能误挂。系统对全部 883 条推导关系标注 `parentEvidence: heuristic`，并在校验中心集中列出，供人工逐一核对。

2. **无法判定处一律留白，不做猜测**。例如原谱第 6 页第 326 行的 `E326`–`H326` 连续四格「万氏／宋氏／宫氏／崔氏」未记明夫主，系统标记为待考错误而非猜测归属；30 名未循辈分字命名者亦只提示复核，不自动改名。

3. **本转录不改动原文一个字**。所有谱名、旁注、地名、人名均按原样保留（含异体字与生僻字，如「繡xiu」保留注音形式）。凡字表中「道公公」「士仁公」等称呼亦照录原文。

### 4.3 已知转录局限

| 局限 | 说明 |
| --- | --- |
| 合并单元格语义 | 64 处合并区间已记录坐标，但其**视觉跨列含义**（如一个名字横跨两代）需人工判断，脚本未做自动推断 |
| 图形元素 | doc 中的内嵌图片以【图】占位，未做 OCR |
| 手写批注 | 若原件存在手写批注，xlsx 电子版中已不可见，本项目无法还原 |
| 印刷体误认 | 生僻字若在原始录入时即被误录，本项目无从发现，需对照纸质原谱核对 |
| 同名同世 | 全谱 128 组「同名同世而异父」（295 人），系统拆为独立记录并保留各自父系（V005/V016），请人工抽查确认——**这是命名事实，不是数据缺陷** |

> **这些局限是被"框住"而不是被隐藏的**：独立交叉校验（C01–C12）把「转录本身是否忠实」与「原谱本身是否有缺口」分成两类证据——前者必须全绿，后者以 `knownGaps` 逐条列明理由。上表中的每一条局限，都能在校验报告中找到对应的可验算口径。

### 4.4 错行排查：根因、修复与防复现

#### 4.4.1 根因（不是个别格子写错，而是规则本身的系统性缺陷）

原谱是二维网格：父在上一世代列，**一位父的子女自其行位起连续书写**，父大致
位于其子女块的中点。最初的挂接规则 R5 是「逐人取行距最近的父」——它只看单个人，
看不见「块」。于是在**块边界**处，某个子女离**块外的相邻父**反而更近，便被判给了
那位父。典型即第 5 页 J271「世义」：其所在子女块为 J271–J282，块内唯一的父是
庆裕（I276）；但块外的怀裕（I269）行距更近（2 < 5），世义遂被错判给**无嗣的怀裕**。

- 一句话根因：**逐人最近会把一个连续子女块从其边界劈开，把边缘子女送给相邻（常为无嗣）的父。**
- 这不是「第 5 页那一格错了」，而是所有存在「无嗣父 + 相邻多子父」的页面都可能发生的**同类缺陷**。

#### 4.4.2 修复：单一父块修正（最小干预）

在原谱版式上，「一位父的子女连续书写」意味着：

1. 同一（页, 列）上，行差 ≤ 3 的极大连续段即一个**粗块**（须计入**配偶格**——配偶占行、决定块是否连续）；
2. 若某子女所在粗块内**只有一位父**，则该块子女必然全部归他——块不可再分。

实现为「逐人行距最近 **+** 单一父块修正」，且**只否决「最近父落在块外」这一种情形**，
其余一律维持逐人原判。这一点至关重要：若让块归属**全面替换**逐人判定，会连带改动
大量本无问题的挂接（实测 24 处父系漂移，其中跨页重复出现者因两页块划分不同而被误拆为两人）。
故采**最小干预**——只有「父既已不在块内，说明该父在此处无嗣，名额应让给块内的父」时方作纠正。

修正共纠正 **12 处**（V017 逐条留档），其中包含作者核定的第 5 页「世义 → 庆裕」。

#### 4.4.3 防复现（三重闸门）

| 闸门 | 位置 | 作用 |
| --- | --- | --- |
| **V017** 单一父块修正清单 | 构建期校验 | 逐条列出被块修正的挂接；该列表异常增减即说明块约束失效，应立即排查。 |
| **V019** 空巢父待考清单 | 构建期校验 | 列出「有配偶却名下无子女、而紧邻下一位父有 ≥2 子女」者（当前 12 处）。这是错行的**残余风险信号**，新增即报警。 |
| **C07** 启发式父系可解释性 | 独立交叉校验 | 独立重算 948 处出现格，验证**每位启发式父必落在其子女的候选集内，或属单一父块例外**；无法解释者必须为 0。 |

> 三重闸门分属三套互不共享代码的实现（构建脚本 / 独立校验脚本 / 诊断脚本），
> 任何一方与另两方不一致都会暴露，故「同类问题复现」会被立即发现而非静默通过。

#### 4.4.4 诊断结论（`tools/diagnose_alignment.py`）

| 类别 | 数量 | 说明 |
| --- | :-: | --- |
| A 空巢父 | 12 | 有配偶却名下无子女，且紧邻下一位父有 ≥2 子女。**待考**：多数系原谱本就未记其子嗣（少亡、失载），非必为错。 |
| B 行块交错 | **0** | 已无「同一父的子女被别的父打断」的情形。 |
| C 远距挂接 | **0** | 已无「子女与父之间隔着别的父且行距 > 12」的情形。 |
| D 过继改位 | 2 | **正常现象**：出继子按原谱惯例列于**养父行位**，故与生父行距天然很大。 |

**关键订正**：此前 B=2、C=2 并非错行，而是**过继的版式后果**——

- 第 14 页「爱德」G901：其生父为道君（F946），却出现在**养父道春**（F901）的行位；
  第 16 页 H1050 旁注明载「**过继给道春为子**」，并注「见14页」。
- 第 27 页「万昌」E1861：其生父为士达（F1879），却出现在**养父士财**（F1862）的行位；
  第 27 页 F1862 旁注明载「**为士达次子过继**」。

二者在建模中均已正确立为 `adoption` 关系（爱德→道春、万昌→士达），只是诊断脚本
原先未识别「出继子可改位」这一原谱惯例，故误报。现已加入**过继豁免**并单列 D 类。

> 注：此前未做 per-page 去重时，C 类曾虚报 110 处；修复跨页回退后降至 2 处，
> 再引入过继豁免后归 0。完整输出见 `data/alignment-risk.txt`（28 行）。

#### 4.4.5 规则量化对照（`tools/compare_rules.py`）

以**文献明载 / 主干行 / 作者核定**的 61 例父子关系为标准答案：

| 规则 | 命中率 | 说明 |
| --- | :-: | --- |
| R 纯逐人行最近 | 56/61 = **91.8%** | 会被块边界劈块误导。 |
| **S 现行发布（逐人 + 单一父块）** | 57/61 = **93.4%** | 作者核定的「世义 → 庆裕」一例由 R 的错判纠正为正确。 |
| D 区块 + 单调 DP（**已否决**） | 54/61 = 88.5% | 目标 Σ\|块中位数 − 父行\| 会灾难性并块（第 7 页 14 名子女全判给「纹」），故弃用，仅留档比对。 |
| B 建模产物（含 doc/spine/author 覆盖） | 61/61 = 100% | 最终发布结果。 |

结论：**块约束是对的，但必须只用于「否决块外的最近父」，不能整体替换逐人判定。**
