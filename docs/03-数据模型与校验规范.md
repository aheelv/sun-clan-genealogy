## 第一部分：数据模型

### 1. 设计原则

| 编号 | 原则 | 说明 |
| --- | --- | --- |
| **P1** | 单一事实来源 | 人物（`persons`）为 SSOT；父子/婚姻关系由字段**派生**，不重复存储，杜绝"关系表与人物表打架" |
| **P2** | 溯源优先 | 每条记录保留原谱出处 `[页, 行, 列, 原文]`，可回溯到 xlsx 的具体单元格 |
| **P3** | 置信度显式化 | `explicit`（原谱明载）与 `inferred`（规则推导）严格区分，绝不混同 |
| **P4** | 枚举收敛 | 性别、状态、支系、证据类型均为**闭集**，新增取值必须修改 `schema.js` |
| **P5** | 权限即模型 | 每个字段在模型中标注 `access` 权限键，字段级访问控制成为模型一等公民 |

### 2. 实体

```
Person ──┬── fatherId ──▶ Person            (父系，单亲单线)
         ├── spouseOfId ──▶ Person          (夫主，仅配偶身份填写)
         ├── spouseIds[] ──▶ Person          (配偶列表，反向引用)
         ├── childrenIds[] ──▶ Person        (子女，冗余缓存，以 fatherId 为准)
         └── refs[] ──▶ [page, row, col, raw] (原谱出处)

Adoption { fromId, toId, ... }              (过继：独立关系，不改变父系归属)
```

**为什么过继单独存储？** 过继（出继/承继）不改变一个人的父系血统归属，只是增加一重社会关系。若把它塞进 `fatherId`，会导致世系链断裂、支系归属错误。因此独立为 `adoptions` 数组。

### 3. 字段定义（`PERSON_FIELDS`）

| 字段 | 类型 | 必填 | 约束 | 权限键 | 说明 |
| --- | --- | :-: | --- | --- | --- |
| `id` | string | ✓ | 不可变 | `person:update` | 系统生成的稳定标识（`P`=主干 / `S`=配偶） |
| `name` | string | ✓ | 1–6 汉字，可附拼音；正则 `^[\u4e00-\u9fa5]{1,6}([a-z]{2,6})?$` | `person:update` | 谱名，如「士聪」「繡xiu」 |
| `surname` | string | | 0–2 汉字 | `person:update` | 男性默认「孙」；配偶填娘家姓 |
| `givenName` | string | | ≤6 字 | `person:update` | 配偶以全名记载时的名（如「德贤」） |
| `gender` | enum | ✓ | `M` / `F` / `U` | `person:update` | 乾 / 坤 / 待考 |
| `isSpouse` | bool | ✓ | `true` / `false` | `person:update` | 是否配偶身份 |
| `gen` | int | ✓ | 1–18 | **`person:structure`** | 世代。一世祖文友公为第 1 世 |
| `branchId` | enum | ✓ | `BR-ROOT`/`BR-REN`/`BR-LI`/`BR-YI`/`BR-ZHI`/`BR-BIN`/`BR-JI`/`BR-UNDEF` | **`person:structure`** | 支系归属 |
| `status` | enum | ✓ | `normal`/`少亡`/`孤`/`无后` | `person:update` | 源自原谱旁注 |
| `pinyin` | string | | ≤12 字 | `person:update` | 生僻字注音 |
| `fatherId` | ref | | 指向 Person | `relation:write` | 留空 = 世系断点，校验中心会提示 |
| `spouseOfId` | ref | | 指向 Person | `relation:write` | 仅配偶身份填写 |
| `spouseIds` | refList | | Person[] | `relation:write` | 配偶列表（系统维护） |
| `notes` | json | | `[{type, text}]` | `person:update` | 旁注 |
| `refs` | refs | | `[page,row,col,raw][]` | `person:update` | 原谱出处 |

**结构性字段（`gen` / `branchId`）单列 `person:structure` 权限**：它们决定全谱骨架，一旦误改会引发大面积「世代跳跃」与「支系不一致」错误，因此编修角色不得触碰。

| 键 | 标签 | 强度 | 来源 |
| --- | --- | :-: | --- |

### 5. 派生字段（不入库）

## 第二部分：推导规则（R1–R10）

原谱图表是**空间布局**而非结构化数据：世代由列位置隐含，房支由行位置隐含，关系靠相邻性表达。`tools/build_data.py` 通过以下规则把空间语义还原为谱系语义。

| 规则 | 名称 | 内容 | 证据强度 |
| --- | --- | --- | :-: |
| **R1** | 页内世代 | 页与世代均从**版式标记**读取：含「孙氏世系图表 第 NN 页」的行切分页面（共 31 页）；紧随其后的**表头行**逐列给出「N代」字样（正则 `^[一二三四五六七八九十]+代$`），据此建立 `列 → 世代` 映射 | — |
| **R2** | 配偶归属 | 同列紧邻其后的「X氏」单元格 = 该列主干的配偶 | `adjacency` (3) |
| **R2a** | 凡字判性 | 第 6–15 世凡字严格：主干单元格的**名字不含本辈凡字**，且**同一列紧邻前一格**（行距 ≤ 2）为男性 → 该格改判为配偶 | `adjacency` (3) |
| **R3** | 注记归属 | 注记归属**列位感知**的同页人物：原谱旁注写在被注人**自己的列**或其**次代列（列号 +1）**，行号相同或相邻。按 `(是否本列/次代列, 行距, 列距)` 分层排序取最近者 | — |
| **R4** | 主干行 | 一行内横向连续填写的单元格 = 一条**显式世系链**（共检出 32 条主干行，贡献 51 条明载父子关系） | `spine` (2) |
| **R5** | 启发式父子 | 父 = **相邻世代列**中行距最近的男性；**再加「单一父块」修正**——子女所在粗块（行差 ≤ 3，含配偶格）内只有一位父时，该块子女全部归他 | `heuristic` (1) |
| **R6** | 文献覆盖 | 《前言》明载的世系链（文友→元亨/元贞→仁/义/礼/智/斌/吉）硬编码为最高优先级，**覆盖** R5 的推导结果 | `doc` (3) |
| **R7** | 支系传播 | 支系 = 三世祖支系头名；其余沿父系继承 | — |
| **R8** | 同名异人键 | **同名 + 同世代 ≠ 同一人**。实体归并键为递归身份键 `pkey(人) = (世代, 姓名, pkey(父))`；原谱「同名／重名」旁注可**显式**区分同名者 | — |
| **R9** | 过继旁注 | 旁注「过继给 X 为子」**指名养父**：`fatherId` 保持为生父，另立 `adoption` 关系（出继子 → 养父） | `note` (3) |
| **R9b** | 生父旁注 | 旁注「为 X 之 N 子过继」「（X 之 N 子过继）」**指名生父**：X 写入 `fatherId`（与 R9 方向相反，故规则须先于通用「过继」匹配） | `note` (3) |
| **R10** | 组内定父 | 归并组内以 `pkey` 判定父系是否真有分歧；有分歧时按**证据强度**择优统一：`note`(4) > `doc`(3) > `spine`(2) > `heuristic`(1) | — |

### R2a 详解（本谱最关键的启发式规则）

**问题**：谱中早期世代记女性为「X氏」，但**后期世代改记女性全名**（如「迟德贤」「桑凤兰」「秦福莲」）。若不加处理，这些女性会被当作主干男丁，导致凡字校验出现大量假阳性（初版为 368 例）。

**解法**：对第 6–15 世（凡字严格期）的每个单元格：

```
若 名字不含本辈凡字
且 同一列紧邻前一格（行距 ≤ 2）为男性
则 判为配偶（isSpouse = true），而非主干
```

**为何用「紧邻」（行距 ≤ 2）而非宽松窗口？** 初版用 `limit = 6` 的宽松窗口，导致「某男性的儿子恰好名中无凡字」时也被误判为配偶。收紧为严格相邻后，假阳性从 368 例降至 15 例，最终收敛为 30 例「未循辈分字命名」警告（这些确为需要人工考证的真实疑点）。

### 实体归并

**归并键**：`pkey(人) = (世代, 姓名, pkey(父))` —— **递归人物身份键**。

**为什么不能只用「姓名 + 世代」**：族谱用**凡字**命名，同辈男丁共用一字（十三世皆含「广」），因此「同名 + 同世代」在原谱中**大量存在**，绝不等于同一人。若按姓名归并，分居两支的同名者会被并成一条，配偶与子女随之混作一团。判定的唯一正确依据是**父的身份**；而父本身也可能同名，故须**递归**上溯。父子世代差恒为 1（`V002 = 0`，无世代跳跃），递归必然终止。

**归并的意义**：同一人在原谱中常**跨页重复出现**（206 人有多于 1 条出处，共 2,154 条出处引用）。归并后，多出处合并为同一记录的 `refs` 数组，实现"一人一记录、多页可溯源"。

**分歧检测与归并共用同一函数**：判断「这些出现格是否同属一人」与判断「父系是否有分歧」，必须用**同一个** `pkey`。旧实现前者比姓名、后者比**单元格引用**，于是「同一父亲、不同格子」被误读成「父亲有分歧」，把大量本无争议的人推入拆分分支（`V016` 一度虚高至 182 组）。

**例（同名同世、父名亦同，仍是两人）**：

| 记录 | 世 | 身份键链 | 支系 | 配偶 | 子女 |
| --- | :-: | --- | :-: | --- | --- |
| `P0091` 士彬 | 6 | 士彬 ← **紷(P0037)** ← 国仕 | 礼 | 王氏 | — |
| `P0114` 士彬 | 6 | 士彬 ← **紷(P0045)** ← 国儒 | 礼 | 王氏 | 志昌、硕昌 |

两人的父亲**都叫「紷」**，却是两个不同的人（`P0037` ≠ `P0045`）。只看姓名会误并，看 `pkey` 才能分开。

## 第三部分：校验规范

系统存在**三套互补的校验**：

| 引擎 | 位置 | 运行时机 | 规则集 |
| --- | --- | --- | --- |
| **独立交叉校验** | `tools/verify_data.py` | 离线，与建模脚本**不共享代码** | `C01`–`C12`（12 项） |
| **构建期校验** | `tools/build_data.py` | 离线建模完成后一次性 | `V001`–`V016`（16 项） |
| **误合并排查** | `tools/diagnose_merge.py` | 离线，与建模脚本**不共享代码** | 按版式几何独立重算邻接父，比对是否矛盾 |
| **运行时校验** | `assets/js/core/validate.js` | 表单实时 / 保存前 / 校验中心 | `F-`×4 + `R-`×9 + `G-`×11 = **24 条** |

三者目的不同：

- **独立交叉校验**回答「原始文件的内容抓取准不准」。它不复用建模脚本的任何代码，只凭 `chart-raw.json`（原谱逐格转录）把分页、列→世代映射、主干链、候选父**独立重算一遍**，再与 `genealogy.json` 逐项比对。这是对「谱系关系等关键数据必须确保无误」最直接的证据。
- **构建期校验**回答「转录与建模质量如何」（发现问题即回头改脚本）。
- **运行时校验**回答「使用者编辑后的数据还对不对」（持续守护）。

### 3.1 校验分级

| 级别 | 含义 | 行为 |
| --- | --- | --- |
| `error` | 阻断性错误 | **拒绝保存**；必须在界面提示并阻止写入 |
| `warn` | 可疑但可保存 | 提示使用者，允许保存（族谱中确实存在特例） |
| `info` | 供人工复核 | 仅记录，用于集中呈现待考事项 |

### 3.2 独立交叉校验（C01–C12）

| 编号 | 校验项 | 独立重算方式 | 结果 |
| --- | --- | --- | :-: |
| C01 | 单元格往返 | 每条出处指向的单元格，其原文须与记录 `raw` 完全一致（2,154 条） | ✓ |
| C02 | 页码归属 | 出处标注的页码须与行号所在页一致（重建 31 页） | ✓ |
| C03 | 世代与列一致 | 人物世代须等于其所在页该列的世代（1,519 处） | ✓ |
| C04 | 单元格全覆盖 | 非空格 = 标题 31 + 表头 496 + 引用 2,251 + 空白 1 = 2,778 | ✓ |
| C05 | 主干链闭合 | 独立重走主干行 32 条、相邻关系 108 处（104 父系链 + 4 过继链） | ✓ |
| C06 | 文献链核对 | 《前言》明载 8 条父子须存在且证据为 `doc` | ✓ |

#### 记录级 `R-`（10 条，保存前 + 全谱校验时逐条触发）

| 规则 ID | 级别 | 名称 | 判定 |
| --- | --- | :-: | --- |

| `R-SPOUSE-ROLE` | warn | 配偶身份标记 | 指定夫主者须标记 `isSpouse` |
| `R-SPOUSE-EXCLUSIVE` | error | **配偶字段互斥** | `spouseOfId`（上向）与 `spouseIds`（下向）不可同时非空；且不得含自身 |
| `R-UNNAMED-NAME` | info | 未具名人物 | 乳名/排行占位需补录 |
| `R-GENCHAR` | warn | 辈分字（凡字） | 主干男丁名含本辈凡字 |

| `R-STATUS-ORPHAN-SPOUSE` | warn | 少亡却有配偶 | 「少亡」不应有配偶 |
| `R-LIFESPAN` | error | 生卒年 | 卒年 ≥ 生年 |

> **`R-SPOUSE-EXCLUSIVE` 的来历**：独立交叉校验的 C10 曾一次性报出 766 例不一致——配偶的 `spouseIds` 里存了自己的丈夫，导致界面把丈夫渲染两次。根因是建模时双向都写。修法是确立不变量：**`spouseOfId`（配偶 → 夫主，上向）与 `spouseIds`（夫主 → 配偶，下向）互斥**，配偶自身的配偶列表恒为空，其夫主一律由 `spouseOfId` 表达。该规则即为此不变量的运行时守卫。
>
> **实现要点**：`validateRecord()` = **字段级规则 + 记录级规则**。若只跑记录级规则，「空姓名」这类必填错误会在保存前被漏掉（初版即有此缺陷，被逻辑层自检捕获）。两者合并后，表单实时校验与保存前校验共用同一套字段口径，不会出现"表单说合法、保存时又说非法"的漂移。

## 第四部分：校验的工程价值

### 4.1 校验驱动了建模本身的改进

本项目的推导规则不是一次设计完成的，而是**被校验结果反复逼出来的**：

| 阶段 | 现象 | 诊断 | 引入的规则 |
| --- | --- | --- | --- |
| 初版 | 支系分布畸形（斌 74 人、义 1 人、吉 1 人） | 归并组内选了**代际最小**的候选父，而非**证据最强**的 | **R10** 组内定父（按证据强度择优）+ R8 + R9 |
| 二版 | 凡字不符 368 例（假阳性过多） | 后期世代女性**以全名记载**，被误判为主干 | **R2a** 凡字判性 |
| 三版 | 凡字不符 30 例（仍偏多） | 宽松窗口（`limit=6`）误伤"名中无凡字的儿子" | R2a 收紧为**严格相邻**（行距 ≤ 2） |
| 四版 | 凡字不符 30 例，全部为真实疑点 | 收敛 | — |
| **五版** | **独立交叉校验 C10 报出 766 例配偶不一致** | 配偶的 `spouseIds` 里存了丈夫，界面重复渲染 | **配偶字段互斥不变量** + `R-SPOUSE-EXCLUSIVE` |

| **七版** | **V014 仍误报 27 例** | ① 比较的是「出现格 id」而非父名；② 差异其实可由过继解释 | V014 改为按**父名**去重比较，并排除「每个不同父都是某人的 fatherId 或过继对象」的组 → 收敛为 **1 例真实冲突** |
| **八版** | **过继关系 15 条，但唯一对只有 12 组** | 同一「出继→养父」关系跨行跨页重复出现，`add_rel` 未去重 | 按 `(出继子, 养父)` 去重；重复次数另计 |
| **九版** | **布局引擎父节点仅 34% 居中于子节点** | 朴素「子树矩形打包」无法处理「主干 + 右侧配偶」的左右不对称单元 | 改用**轮廓法**（Reingold–Tilford 思路），居中率 → **100%**，树宽收窄 28% |

### 4.2 校验结果的可追溯性

每条问题都带 `personId`，界面可一键跳转到该人物档案；人物档案中又可查看其原谱出处（页码 + 单元格引用）——形成 **问题 → 人物 → 原谱单元格** 的完整追溯链。使用者不必相信系统的判断，可以自己回到原谱核对。

### 4.3 「不猜」原则

系统在所有不确定处**显式留白**而非填补：

- 884 条启发式父子关系全部标注 `parentEvidence: heuristic`，并在校验中心集中列出；
- 4 名无法确定夫主的配偶标记为 `error` 待考，不猜测归属；
- 10 条未归类旁注原样保留，不强行套用已知类型；
- 30 名凡字不符者不自动改名，只提示复核；
- 128 组同名异人**不按姓名合并**，各自保留独立父系，交由人工抽查确认。

族谱是**不可再生**的史料。宁可留下待考标记，也不制造看似完整实则错误的谱系——这是本项目的核心工程伦理。
